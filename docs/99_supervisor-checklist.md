# 監督専用チェックリスト

<!-- ★これはあなた（監督）専用です。sys-staff にも sys-junior にも渡さないこと。
     渡すと「答えを知っているシステム担当者」になり、ヒアリングの練習になりません。
     アクセスは .claude/hooks/audit.py が記録しています。 -->

`sys-staff` が作る質問リストや設計が**何を落としているか**を判定するための材料です。
これと突き合わせて、抜けていたら `/steer` で気づかせるか、あえて放置して破綻を観察します。

**★印は `docs/90_ground-truth.md` に実際に仕込みがある項目です。** 掘れば必ず何か出てきます。
無印は一般論として押さえるべき観点で、業務側が特に用意していないもの。

---

## ⓪ 前提の確認

- ★ **紐づけキーは何か。1件の受付に車検証が複数枚あるケースはあるか**（1:N。聞かないと出てこない）
- ★ 突合の対象項目をどれにするか（「大事なのは数項目」としか言われない）
- ★ 締めの正確な日と時刻（「月末あたり」しか返ってこない。宿題化が正解）
- ★ 何人で回すか、どう分担するか
- 1件あたりの想定作業時間（誰も知らない。仮決めするしかない）
- 車検証記録事項の帳票そのものを見せてもらったか（現物確認）

## ① 取込

- 同じファイルを2回取り込んだらどうなるか（冪等性）
- 取込途中でエラーが出たら、正常分だけ入れるか全件やめるか
- 取り込んだデータの取り消し・やり直しは誰ができるか
- ★ **文字コード**（Shift_JIS か UTF-8 か。基幹システムの出力に依存）
- ★ **全角半角・旧字体・㈱・ハイフン種別の正規化をどこでやるか**（マッチング精度の根幹）
- **OCRの信頼度スコアを使うか**（`12_briefing.md` に「項目単位で出せる」と書いてある。システム側の持ち札なので、使わないのは機会損失）
- 受付データとOCRデータの取込順序に依存があるか
- CSVの項目定義書は入手できているか

## ② マッチング

- ★ **和暦と西暦の混在**（帳票は和暦、受付データは西暦。気づかないと全件不一致）
- ★ **完全一致だけで判定すると全角半角で落ちる**
- ★ **車台番号をキーにしてよいか**（読み間違いが多い項目をキーにする危険）
- ★ **1:N のカーディナリティ**
- 結果の状態は何種類か（完全一致／要確認／不一致／候補複数／対象外）
- ★ **再突合したときに、人が確定済みの内容を上書きするか**（最大の地雷。聞かないと誰も気づかない）
- 複数候補が並んだときの優先順位
- 突合対象外にすべきデータ（取消分、テスト分）の判定条件
- 期ズレ（先月の受付と今月のOCR）の扱い

## ③ データ修正

- ★ **自動修正は絶対に受け入れられない**（部長が強く拒否する。提案すると心証を悪くする）
- ★ **監査ログ（誰が・いつ・何を・何から何に）**。聞かないと出てこないが、無いと分かると強く反応される
- ★ **修正前の値を残すか**
- ★ **複数人が同じ件を同時に開いたときの排他制御**（業務側は考えていない。案を出すのはこちら）
- ★ **確定の取り消しを許すか、誰が取り消せるか**
- 修正できるのは何か（OCR側／受付側／紐づけだけ）
- 手動での強制マッチ・紐づけ解除
- 同じ誤読の一括置換（あると便利だが50件では必須ではない）
- 入力チェック（桁、型、マスタ存在）

## ④ 出力

- ★ **レイアウトは基幹システムが受け付ける形に従う**（こちらで決められない。仕様書の入手が宿題）
- ★ **文字化け**（過去に別ツールで化けた経験がある。強く反応される）
- ★ **未確定のものを含めない**
- ★ **二重出力の防止**
- ★ **出力後に修正が入ったらどうするか**（業務側は考えていない）
- ★ 対象0件のときファイルを作るか（基幹システム側の仕様次第）
- 再出力の可否とファイル名の付け方
- 出力済みフラグを持つか

## ⑤ 画面・UI（C# WinForms）

- ★ **保存のタイミング**（都度保存か確定ボタンか。業務アプリで必ず揉める）
- ★ **項目名は車検証の正式名称で**（「車体番号」と書くと部長に指摘される。正しくは「車台番号」）
- キーボード操作主体か（業務系は Enter で次項目、ファンクションキー）
- 未保存で閉じたときの警告
- 一覧の表示件数（50件なので仮想化は不要。過剰設計を疑う）
- 状態の色分けと、色以外の識別手段
- 画面間の一貫性ルール（ボタン位置、日付書式）を先に決めたか
- インストール方式と更新の配り方

## ⑥ 非機能・運用

- ★ **50件/月という規模に見合っているか**（過剰な作り込みは管理者が削りにくる）
- 権限（誰が確定でき、誰が取り消せるか）
- データ保持期間とバックアップ
- 障害時のリカバリ手順
- 前後のシステムが変更されたときの影響

## 進行の質を見るポイント

| 見るところ | 崩れているサイン |
|---|---|
| **決定権の確認** | 部長がいるうちに委譲確認をしたか。しなければ以降ずっと「部長に確認します」になる |
| **二つの壁の見分け** | 「知らない」に部長確認を求めていないか。「権限がない」に案を出していないか |
| **開いた質問の空振り** | 「どうしますか」を繰り返していないか。選択肢提示に切り替えられているか |
| **仮決めの活用** | 未決を全部宿題にしていないか。宿題だけが増えて決定が残らない |
| **根拠発言の紐づけ** | `/decide` で `--utterance` を付けているか。無い決定は蒸し返しに勝てない |
| **社内レビュー** | 新人の画面を素通しで業務担当者に出していないか |
| **進行と中身の分離** | `sys-staff` が「次の議題に移ります」と仕切っていないか（それは司会の仕事） |
| **規模感** | 50件/月に対して過剰な機能を提案していないか |
