# 聞き出しの作法（新規案件の要件ヒアリング）

`sys-staff` が主に使う。`sys-junior` は「7. 設計で詰まったことを質問に変える」だけ読めばよい。
**質問リストを作る前に、このファイルを最後まで読むこと。**

## 1. 新規案件では、聞くだけでは何も出てこない

現行業務がないため、**業務側も答えを持っていません**。部下の業務イメージは4割程度です。
開いた質問をすると「まだ決めていません」が返り、会議が空転します。

だから主技法が変わります。**聞くのではなく、当てる。**

| 型 | 使う場面 | 効果 |
|---|---|---|
| **クローズド変換** | 方針・方式を決めたい | 選択肢には反応できる。「決めていない」が「たぶんBです」になる |
| **具体例で当てる** | 例外・境界を掘りたい | 抽象だと出てこない例外が、ケースを見せると出てくる |
| **仮決めで進む** | 決まらないと分かったとき | 未決を全部宿題にすると、宿題だけが増えて何も決まらない |

## 2. 開いた質問をクローズドに変換する

| やってはいけない | やるべきこと |
|---|---|
| 「不一致が出たらどうしますか」 | 「A案：その場で直す／B案：一覧に溜めて後でまとめて直す。どちらが業務に近いですか」 |
| 「出力はどんな形式が必要ですか」 | 「基幹に返すCSVと、確認用のExcel。両方要りますか、片方でいいですか」 |
| 「誰が使いますか」 | 「担当者3人が同時に触りますか、1人が順番に処理しますか」 |
| 「例外はありますか」 | （3節へ。例外は聞くものではなく、具体例で掘るもの） |
| 「運用はどうなりますか」 | 「毎日決まった時間に取り込みますか、データが来たら都度ですか」 |

守ること:

- **選択肢は2〜3個。** 4つ以上は選べません
- **それぞれの帰結を添える。** 「A案だとその場で直せますが、担当者が判断を持つことになります」。帰結が無い選択肢は勘で選ばれ、後で覆ります
- **「その他」を必ず残す。** 用意した案が全部外れることがあり、**そこにこそ業務の実態があります**
- 選択肢を出すことは、こちらが業務を仮定することです。**外れたら訂正が返ってくる。それが収穫です**

## 3. 具体例で例外を掘り起こす

抽象的に聞かず、ケースを作って当てます。効くのは**面倒な例**です。

| 例の作り方 | 具体例 | 引き出せるもの |
|---|---|---|
| 境界値 | 「金額が1円だけずれていたら、一致扱いにしますか」 | 許容誤差の有無 |
| あり得ない値 | 「OCRが金額をマイナスで読んだら、止めますか通しますか」 | エラー処理の方針 |
| 重複 | 「同じ方が同じ日に2件受け付けたら、どう見分けますか」 | 突合キーの妥当性 |
| 欠損 | 「車検証の項目が1つ読めていなかったら、その1件はどう扱いますか」 | 部分エラーの扱い |
| 例外運用 | 「月末に件数が跳ねたとき、その日のうちに終わらせる必要がありますか」 | 性能・運用要件 |

- **二択で当てる。** 「どう扱いますか」ではなく「止めますか、通しますか」
- **反応が薄いのは、例が業務から遠い証拠。** もっと日常的な例に変えます
- 業務側が「それは無い」と即答したら、それも収穫です。`fact` に記録します

## 4. 二つの壁を見分ける

部下が「決められない」と言うとき、理由は2つあり、**突破法が違います**。取り違えると会議が詰まります。

| 壁 | 症状 | 突破法 | 取り違えると |
|---|---|---|---|
| **権限の壁** | 「部長に確認します」「私では決められません」 | 部長がいるうちに決定権を委譲させる。いなければ確認枠を使うか宿題に | 案をいくら出しても「確認します」が返り続ける |
| **知識の壁** | 「そこまでは把握していません」「まだ決めていません」 | **案を作って当てる**（2節・3節） | 部長に確認しても、部長も知らない |

見分け方: **調べれば分かることか、誰かが決めなければ分からないことか。**
前者は知識の壁（案を当てる）、後者は権限の壁（決裁を取る）。

**決定権が下りているかは `docs/04_established-facts.md` の決定権ステータスで確認できます。**
「未確認」のままなら、判断を伴う質問はすべて権限の壁に当たります。部長がいる会議で先に委譲を取り付けてください。

## 5. 質問リストの書き方

置き場所は `docs/00_question-list.md`。**その会議の目的に合わせて、会議前に作ります。**

`/next` は引数がなければこのリストの順に議題を進めます。**上から順に会議で使える並び**にしてください。

### 順序の決め方

1. **★決定必要**かつ**相手が `client-boss`** のもの ── 部長は冒頭で退席します。**ここで聞き損ねたら、その会議ではもう決まりません**
2. 決定権の委譲そのもの（部下の判断を部長の決定として扱ってよいかの確認）── 実際には最初の1問
3. ★決定必要で相手が `client-staff` のもの
4. ☆参考（背景理解のため。決定は要らない）

**1回の会議で消化できるのは2〜3論点です。** 10問並べても構いませんが、上から3問が本命になるよう並べてください。

### フォーマット

````markdown
# 質問リスト（第2回：マッチング条件を詰める）

**作成**: sys-staff / **想定論点**: 3

## Q1. 部下の判断を部長の決定として進めてよいか  ★決定必要 / 相手: client-boss（冒頭のみ）

（決定権の委譲。**部長がいる最初の会議で必ず聞く**）

## Q2. 突合のキーは何か  ★決定必要 / 相手: client-boss（冒頭のみ）

受付データとOCR CSVを、何で結びつけるか。

- **A案: 受付Noで1対1** — 確実。ただしOCRが受付Noを読めないと全件不一致になる
- **B案: 氏名＋受付日＋金額の複合** — 読み取り漏れに強い。ただし同姓同名で誤突合の恐れ
- **C案: A案で突合し、外れたものだけB案で候補を出す** — 実装は重いが運用に近い
- その他:

**具体例**: 「同じ方が同じ日に2件受け付けたら、B案では区別できませんが、これは起きますか」

## Q3. 不一致をいつ直すか  ★決定必要 / 相手: client-staff

...

## Q4. 月あたりの件数の変動  ☆参考 / 相手: client-staff

...
````

### 各質問に必ず入れるもの

| 要素 | なぜ要るか |
|---|---|
| 見出しの質問文 | **そのまま `/next` の議題名になります。** 一文で言い切ること |
| ★決定必要 / ☆参考 | 決定が要るものを、決裁者がいるうちに片づけるため |
| 相手 | **部長退席後には聞けないものを見分けるため** |
| 選択肢A/B/C＋各案の帰結 | 選ばせるため（2節） |
| その他: | 仮定が全部外れたときの受け皿 |
| 具体例 | 例外を掘るため（3節）。★の質問には必ず1つ付ける |

## 6. 会議での出し方

- **一度に3〜5問まとめて聞く。** 1問ずつ聞くと会議が進みません
- リストを読み上げない。**その場の流れに合う順に組み替えて構いません**
- 相手が具体を語り始めたら、リストを離れて掘ります。**リストの消化が目的ではありません**
- 議事進行の発言（「では次の議題に」「時間がないので」）はしない。それは司会の仕事です
- 会議で新しく生まれた疑問はリストに追記します。次回の入口になります

## 7. 設計で詰まったことを質問に変える（`sys-junior` 向け）

**手を動かしてから出る質問のほうが、具体的で鋭くなります。**

| 弱い質問（知らないから聞く） | 強い質問（詰まったから聞く） |
|---|---|
| 「マッチングって何ですか」 | 「この一覧、不一致だったときに何を出せばいいのか分からなくて手が止まりました」 |
| 「状態にはどんな種類がありますか」 | 「状態を『一致・不一致』の2つで作ったんですが、『候補』みたいな中間は要りますか」 |
| 「検索条件は何が要りますか」 | 「担当者で絞る条件を付けたんですが、これは実際に使いますか」 |

先に画面を作り、埋められなかった欄をそのまま質問にしてください。
`screen-design` スキルの項目定義で「未確定」と書いた欄が、そのまま質問の種です。

## 8. 決まったら記録する

**決定には根拠発言IDを紐づけます。無い決定は、蒸し返されたときに守れません。**

発言IDは検索して調べます。

```bash
python scripts/query.py 突合キー --utterances-only    # 発言IDを探す
python scripts/query.py --utterance 42                # 前後の文脈を確認
```

| 決まり方 | 記録 |
|---|---|
| 決める権限のある人が、その場で明言した | `--status 本` |
| 部下が答えたが決定権ステータスが「未確認」 | `--status 仮` |
| 案を出して「たぶんそれで」と言われた | `--status 仮` |
| 業務の事実を教えられた（決定ではない） | `fact` に記録 |
| 決まらなかった | `issue`（宿題）。ただし**全部これにしない** |

```bash
python scripts/record.py decision --body "突合キーは受付Noを主とし、外れた分は複合キーで候補提示" \
  --status 仮 --by client-staff --utterance 42
python scripts/record.py fact --topic 件数 --body "月50件前後。月末に集中する" --utterance 38
python scripts/record.py issue --body "OCRの読み取り精度の実績値を確認する" --owner client-staff --due 2026-09-05
python scripts/views.py
```

**本決めにできるのは、決める権限のある人がその場で明言したときだけです。** それ以外は仮決めにします。
仮決めは `/meeting-open` のたびにリマインドされ、後で本決めに昇格できます。

## 9. やってはいけないこと

- **`docs/90_ground-truth.md` を読む。** 答えを知っている者が質問したらシミュレーションが無意味になります
- 1問ずつ聞く
- 開いた質問を並べる（「〜はどうしますか」が3つ続いたら、リストを作り直す）
- 未決を全部宿題にする
- 部長がいるうちに聞くべきことを後回しにする
- 質問リストを最後まで消化しようとする（時間内に2〜3論点が限度）

要件が固まってきたら `screen-design` スキルへ。**聞き出した内容を画面にして当てるのが、次の確認手段になります。**
