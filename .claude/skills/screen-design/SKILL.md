# 画面設計の作法（C# WinForms 業務アプリ）

`sys-staff` と `sys-junior` が共用する。**設計に入る前にこのファイルを最後まで読むこと。**

## 1. 設計の順序

1. **その画面を誰がいつ使うか**を一文で言えるようにする（`docs/10_tobe-flow.md` の業務フロー上の位置）
2. **その画面で完了する仕事**を決める。1画面1目的
3. 必要な情報と操作を洗い出す
4. ワイヤーフレームを書く
5. 項目定義を書く
6. DBに登録する

**1と2を飛ばして絵から描き始めると、業務的に成立しない画面になる。** 検索条件を並べたくなったら「この条件で本当に絞るのか、誰が」を先に確かめること。

## 2. テキストワイヤーフレームの記法

固定幅で書く。実物の比率にこだわらず、**配置と情報の優先順位**が伝わればよい。

```
+-- 突合結果一覧 ------------------------------------------------+
| 対象期間 [2026/08/01]～[2026/08/31]  状態[すべて      ▼] [検索] |
+----------------------------------------------------------------+
| 状態   | 受付No   | 氏名       | 受付金額 | OCR金額 | 差額      |
|--------|----------|------------|----------|---------|-----------|
| 一致   | 00001234 | ...        |   12,000 |  12,000 |         0 |
| 候補   | 00001235 | ...        |   -3,400 |  -3,400 |         0 |
| 不一致 | 00001236 | ...        |    8,000 |   8,100 |      -100 |
+----------------------------------------------------------------+
| 全 2,431 件 / 不一致 87 件            [修正(F4)] [確定(F12)]    |
+----------------------------------------------------------------+
```

記法:

| 書き方 | 意味 |
|---|---|
| `[   ]` | 入力欄 |
| `[ ▼]` | ドロップダウン |
| `[ボタン(F4)]` | ボタン。**ファンクションキーがあれば併記** |
| `( ) / (x)` | ラジオボタン |
| `[ ] / [x]` | チェックボックス |
| 罫線の表 | DataGridView |
| `...` | 実データの例（省略可だが、**1〜3行は具体値を入れる**） |

**具体値を入れること。** 空の枠だけ見せても業務担当者は反応できない。マイナス金額や桁の大きい値をわざと混ぜると、書式の議論が引き出せる。

## 3. 業務系UIの慣行（WinForms）

守らないと業務担当者に必ず指摘される。

- **キーボード操作が主。** Enterで次項目へ、Tabで移動、主要操作にファンクションキー（F1ヘルプ / F4修正 / F12確定 などを画面間で統一）
- **保存のタイミングを明示する。** 都度保存か、明示的な確定ボタンか。**業務アプリで必ず揉める論点**なので、設計時に決めて業務担当者に確認する
- **未保存で閉じようとしたら警告する**
- 一覧は件数を必ず表示する（全件数と、注目すべき件数）
- **大量件数を素の DataGridView に載せない。** 数千件を超えるなら仮想モードか絞り込み前提にし、その方針を画面に書く
- **状態を色だけで表さない。** 色分けはしてよいが、必ず文字（「不一致」など）も併記する
- 排他制御が要る運用なら、他の人が編集中であることを画面上で示す
- エラーはダイアログの乱発を避け、画面内に出す

## 4. 画面間の一貫性ルール

**最初に決めて、全画面で守る。** 「前の画面とボタンの位置が違う」は業務担当者の正当な指摘であり、後から直すと全画面に波及する。

- 確定・実行系のボタンは常に**右下**
- 閉じる・戻るは常に**左下**
- 検索条件は常に**上部**、結果は中央、集計と操作は下部
- 日付書式、金額書式（カンマ、マイナスの表記）は全画面で統一
- 同じ概念には同じ画面名・項目名を使う（「受付No」と「受付番号」を混在させない）

## 5. 項目定義

ワイヤーフレームに出てくる入力項目すべてについて書く。

| 列 | 書き方 |
|---|---|
| 項目名 | 画面上の表示名と一致させる |
| 型 | 文字 / 数値 / 日付 / 日時 / 真偽 / 選択 |
| 桁 | `10` `9,2`（整数9桁小数2桁）など |
| 必須 | 必須 / 任意 / 条件付き（条件を備考に） |
| 初期値 | 空欄なら「なし」と書く |
| バリデーション | 形式・範囲・マスタ存在チェックなど |
| 備考 | 決まっていないことは**「未確定」と明記する**。空欄で流さない |

**未確定を空欄にしない。** 空欄は「確認済みで無し」と読まれる。決まっていないなら書く。

## 6. DBへの登録

プロジェクトルートから実行する。

```bash
python scripts/record.py screen --code SC-02 --name "突合結果一覧" \
  --area マッチング --designer sys-staff --status 設計中 \
  --summary "突合結果を状態別に一覧表示し、修正画面への入口とする" \
  --wireframe "$(cat wireframe.txt)"

python scripts/record.py screen-item --code SC-02 --item "対象期間From" \
  --datatype 日付 --required 必須 --validation "Toより過去" --note ""

python scripts/views.py          # docs/21_screen-design.md を再生成
python scripts/export_excel.py   # 画面一覧・機能一覧.xlsx を再生成
```

画面コードは `SC-01` 形式の連番（**SC-01 から採番する**）。機能区分は 取込 / マッチング / 修正 / 出力 / 横断。

## 7. 承認フローと状態

```
未着手 → 設計中 → 社内レビュー中 → 社内OK → 業務担当者レビュー中 → 承認済
                        ↑                          ↓
                        └────── 差戻し ←───────────┘
```

- **`sys-junior` が設計した画面は、必ず社内レビュー（`sys-staff`）を通してから業務担当者に出す**
- **承認済みでない画面の詳細仕様は書かない。** 差し戻されたら全部やり直しになる
- 業務担当者レビューでの指摘は `record.py review --stage 業務担当者` で記録し、直したら `resolve` する

## 8. モックアップを出すとき

普段はテキストワイヤーフレームで回す（軽く、何度でも直せる）。**承認を取る回だけ** HTML モックアップを Artifact として公開する。実物を見せないと細部のこだわりが引き出せないため。

その際は組み込みの `artifact-design` スキルを併用すること。
