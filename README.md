# 要件定義会議シミュレーション

**帳票突合ツールの要件定義会議を、5体のエージェントに演じさせるプロジェクトです。ツールそのものは作りません。会議をやります。**

新規案件の要件定義で実際に起きること —— 業務側が自分の業務を説明しきれない、部下に決定権がない、新人の画面が差し戻される、「そんなことは言っていない」と蒸し返される —— を再現し、それを捌く練習をするための場です。

---

## あなたの役割：監督

あなたは会議に**参加しません**。演じるのは5体のエージェント、進行と記録はメインセッション（司会）です。
あなたは**外から見て、必要なときだけ手を入れる**役です。

| 誰 | 何をするか |
|---|---|
| **あなた（監督）** | 観察する。方針を与える。決めさせる。記録させる |
| **メインセッション（Claude）** | **司会・書記・ディスパッチャ**。進行と記録に徹し、中身の議論には踏み込まない |
| **5体のエージェント** | 業務担当者（部長）・その部下・システム担当者・新人・管理者を演じる。議論するのは彼ら |

### 監督に判断が返る場面

会議は自動で流れます。**既定（`/auto` が on）で答えないと進まないのは、会議の外側にあたる1つ —— 開会前の招集確認 —— だけです。**
残り4つは司会が自分で判断して進みます。`/auto` を打って off にすると、下の5つすべてであなたの返事待ちになります。

| いつ | 求められること | 答え方の例 | 既定（`/auto` on）では |
|---|---|---|---|
| 開会前 | **招集案の確認**（この面子でいいか） | 「はい」／「今日は部長抜きで」 | **止まる** |
| 開会時 | 司会が判定した**本日のゴール案**の承認 | 「はい」／「決定権の確認を優先して」 | 止まらない（司会が判定して進む） |
| 議題が一つ終わるたび | **続けるか、次へ行くか** | 「続けて」／「次へ」 | 止まらない |
| 決まったとき | **記録の指示** | `/decide <内容>`、決まらなければ `/todo <内容>` | 止まらない（司会が記録する） |
| 終わり | **閉会** | `/meeting-close`（読み合わせと次回の提案が出ます） | 止まらない（**司会が閉会し、備忘を書き出す**） |

止まらない場面でも**平文でいつでも割り込めます。**「部長、それは月に何件くらいですか」と書けば会議は止まります。

### 割り込む手札は3つ

放っておくと会議は空転します。黙って見ているだけの役ではありません。

| 手札 | 使いどころ |
|---|---|
| `/steer <方針>` | `sys-staff` に方針を渡す。「決定権の確認を先にして」「開いた質問をやめて選択肢を出して」 |
| `/steer 巻き戻し` | 直前のやり取りをなかったことにしてやり直す。発言はDBからも消えます |
| **平文で割り込む** | コマンドを使わず、自分で聞く。「部長、それは月に何件くらいですか」 |

### 見るポイント

うまくいっていないサインです。気づいたら `/steer` の出番。

- `sys-staff` が**部長がいるうちに決定権を確認したか** ── 取り損ねると、残り全部が「部長に確認します」で終わります
- **開いた質問を続けていないか** ── 「どうしましょう」では新規案件は答えが返りません
- **部長がいる間、部下に名指しで聞いているか** ── 場に投げた質問には答えません。振れば答えます
- **新人の画面を社内レビューに通したか** ── 飛ばすと差戻しの山になります
- **決定に根拠発言が紐づいているか／仮決めが溜まっていないか** ── `/status` で分かります

観察の材料は `docs/99_supervisor-checklist.md`（**監督専用**）に、司会の運用ルールは `CLAUDE.md` にあります。

## はじめかた

```bash
python scripts/db_init.py     # 初回のみ。DBを作る（既にあれば何もしない）
```

あとは Claude Code のスラッシュコマンドで進めます。

```
/meeting-open 方向性とスコープを決めたい
```

1. **招集案が表で提示される** → 「この面子でいいか」を答える（固定メニューはありません。目的の文面から参加者が判断されます）
2. **開会** → 前回の仮決め・未消化の宿題・決定権ステータスが読み上げられる
3. **議論が進む** → 既定では止まらずに進みます（`/auto` を off にすると議題ごとに続行可否を聞かれます）
4. **決まったことを記録** → 既定では司会が自分で入れます（`/decide` `/todo` で監督から指示もできます）
5. **閉会** → 読み合わせ → 次に開くべき会議の提案 → **備忘の書き出し**（`output/備忘_NN.md`）。`/auto` が on なら司会が自分で閉じます

いつでも `/status` で現在地が分かります。迷ったらこれ。

## 登場人物

| エージェント | 役 | 参加 |
|---|---|---|
| `sys-manager` | システム管理者（システム担当者の上長） | 会議の**冒頭と最後だけ**（ブックエンド） |
| `client-boss` | 業務担当者（部長）。**高圧的**・細かい・意地悪・丸投げ。運用テストユーザ | 目的による |
| `client-staff` | 部長の部下。**業務イメージは40%**。**部長がいる間は黙り**、退席してから質問が出る | 全編 |
| `sys-staff` | システム担当者。質問し、案を出し、画面を設計する。最も多く発言するが**主張は弱く、運用面に鈍く、断れない** | 全編 |
| `sys-junior` | 新人。素朴な質問＋**周辺画面の設計** | 全編 |

### 参加形態

| 形態 | 意味 |
|---|---|
| `full` | 最初から最後までいる |
| `opening` | 冒頭で方向性を語って**退席する**（以降その人には聞けない） |
| `bookend` | 冒頭と最後だけ出る（管理者の典型） |
| `oneonone` | 個別に相談する |

**部長が退席したあとは、部下に判断を求めても決まりません。** 聞くべきことは部長がいるうちに聞く —— これがこのシミュレーションの最初の関門です。

## 会議の流れ

**何回開くかは決まっていません。** 何が決まったかで次が決まります。会議は4つの型
（**要件を詰める** ／ **画面を決める** ／ **仕様を固める** ／ **運用テスト**）で進み、
**次へ進む条件を満たさなければ、同じ型をもう一度開きます。**同じ型が3回続くのは普通です。
方向性・スコープ・成功条件と決定権の所在は、**案件開始時に確定済み**として与えてあります。

**型ごとの目的・招集・次へ進む条件と、日程の目安は [docs/13_meeting-flow.md](docs/13_meeting-flow.md) にあります。**
`/meeting-open` の現在地判定（本日の型と、条件のうち何が欠けているか）と、`/meeting-close` の次回提案は、
どちらもこのファイルを唯一の正として見ています。

## コマンド

| 区分 | コマンド | 何をするか |
|---|---|---|
| **進行** | `/meeting-open <目的> [60分]` | 目的から参加者を判断し、**招集案を確認してから**開会。前回の仮決めと宿題を読み上げる |
| | `/next [議題]` | 次の議題へ。直前の結論を記録し、残りを宿題か仮決めに振り分ける |
| | `/meeting-close` | 読み合わせ → 記録の確定 → 次に開くべき会議の提案 → **備忘の書き出し**（`output/備忘_NN.md`） |
| | `/clock [--detail] [--budget 45]` | 残り時間を見る。持ち時間の変更も |
| | `/auto` | **会議中の監督待ちを畳む／戻す（既定 on）。**off にするとゴール案・議題ごと・記録の指示で止まる |
| | `/steer <指示>` | `sys-staff` に方針を渡す。「巻き戻し」で直前のやり取りをやり直す |
| **記録** | `/decide <内容>` | 決定を記録（**仮／本**＋根拠発言ID）。番号を渡せば仮決めを本決めに昇格 |
| | `/todo <内容>` ／ `/todo <番号> 完了` | 宿題の起票／消化。担当と期限は必須 |
| | `/escalate <相談>` | 会議中に管理者へ緊急相談（**1会議2回まで**） |
| **画面** | `/screen <画面> [--mockup]` | 画面案の提示。既定はワイヤーフレーム、`--mockup` でHTMLモックアップ |
| | `/approve <画面> [差戻し]` | 承認／差戻しを記録。承認は**決定としても**残る |
| | `/excel` | 画面一覧・機能一覧のExcelを再生成して開く |
| **確認** | `/status` | 決定・仮決め・宿題・画面の承認状態・枠の残り・監査を一覧 |
| | `/recall <語>` | 発言・決定・宿題・事実を横断検索。**「言った言わない」を原文で制する** |
| | `/reset [ラベル]` | 記録をリセットして2周目へ（DBはアーカイブされる） |

- **招集に固定メニューはありません。**目的を自由文で書けば、参加者と参加形態が判断されます
- **決定には必ず根拠発言IDが紐づきます。**無い決定は、蒸し返されたときに守れません
- **承認ゲート**：承認済みでない画面の詳細仕様は書けません
- `--mockup` は承認を取る回だけ。`/recall` は部分一致なので、空振りしたら別の語で

## 会議の持ち時間

**1回の会議は既定60分**です。実会議1回分に相当します。

実時間ではなく、シミュレート上の会議時間を数えます。発言ごとに想定所要時間を積み上げる方式です。

| 話者 | 1発言あたり |
|---|---|
| 司会（開会・議題切替・閉会の定型） | 1分 |
| エージェント（質問のまとめ、回答、指摘） | 3分 |
| 監督（あなた）の介入 | 0分（会議時間に含めない） |

**60分 ≒ エージェント18回＋司会4回。議題は4〜6論点が限度です。**

| 残り | 進行 |
|---|---|
| 2/3以上 | 通常 |
| 1/3を切った | 終盤。あと1〜2論点。広げない |
| **5分以下** | **着地に入る。新しい議題を開かない** |
| 0以下 | 時間切れ。決定を記録し、残りは宿題にして閉会 |

**1回で全部決まらないのが正常です。** 随時開催なので次を開けばよい。無理に延長するより、
何が決まって何が残ったかを明確にして閉じるほうが実務に近くなります。
持ち時間を変えたいときは `/meeting-open 出力の仕様を詰めたい 45分で` のように伝えるか、
会議中に `/clock --budget 45` で変更できます。

副次的な効果として、**エージェント呼び出しが1会議8〜12回に収まります**（時間制限が無いと35〜40回）。

## 中心的な仕掛け

このシミュレーションが「うまくいかない」ようにできている理由です。

| 仕掛け | 中身 |
|---|---|
| **決定権ステータス** | 初期値は「**委譲済み**」（案件開始時に確定済みとして与えてある）。「未確認」に戻すと、部下は判断を伴う質問に「部長に確認します」としか答えなくなり、`sys-staff` が部長に明示的に委譲を確認するまで変わらない |
| **二つの壁** | 部下が決められない理由は「**権限がない**」と「**知らない**」の2つ。突破法が違う（前者は委譲を取り付ける、後者は案を出して当てる） |
| **部下の遠慮** | 部下は部長が同席している間、**自分からは何も言わない**。名指しで振られればはっきり答えるが、場に投げた質問には反応しない。部長がいるうちは**名指しで具体的に聞く**しかなく、そこを逃すと詳細は部長の退席後まで出てこない |
| **確認の枠** | 部長への即時確認は1会議2回まで、管理者への緊急相談も2回まで。使い切ったら宿題に回すしかない |
| **仮決め／本決め** | 新規案件は未決が大量に出る。全部宿題にすると何も決まらない。**仮決めして進む**。仮決めは `/meeting-open` のたびにリマインドされ、放置すると運用テストで突かれる |
| **画面の二段レビュー** | `sys-junior` の画面 → `sys-staff` の**社内レビュー** → 業務担当者の承認。社内レビューを飛ばすと差戻しの山になる |
| **承認ゲート** | 承認済みでない画面の詳細仕様は書かない |
| **蒸し返し** | 業務担当者は過去の決定を否定してくる。根拠発言が紐づいていれば原文を引いて防げる。紐づいていなければ守れない |

## ファイル構成

**全ファイルの一覧です。** 詳しい説明はこの下の各節にあります。

```
meeting-demo/
├─ README.md                     このファイル。全体像・登場人物・仕掛け・コマンド
├─ CLAUDE.md                     司会（メインセッション）が必ず守る運用ルール。毎回自動で読まれる
│
├─ db/                           記録の正。会議のすべてはここに入る
│  ├─ meeting.db                 発言・決定・宿題・確定事実・画面・機能（14テーブル）
│  └─ archive/                   /reset のたびに退避された過去のDB。前の周回と比較できる
│
├─ docs/                         読む文書。番号の頭が用途（00=会議 / 10=入力 / 20=成果物 / 90=非公開）
│  ├─ 00_question-list.md        sys-staff が業務側にぶつける質問リスト        …手書き・git管理外
│  ├─ 01_session-log.md          開催履歴。第何回で何を話し、誰が出たか        …自動生成
│  ├─ 02_decision-log.md         決定事項の台帳。仮／本と根拠発言ID            …自動生成
│  ├─ 03_open-issues.md          宿題リスト（担当・期限）と確認枠の残り        …自動生成
│  ├─ 04_established-facts.md    確定事実と決定権ステータス                    …自動生成
│  ├─ 10_tobe-flow.md            To-Be業務フロー。ツールがどこに入るか         …所与
│  ├─ 11_manager-requirements.md 管理者からの要件一覧＝スコープの基準線        …所与
│  ├─ 12_briefing.md             管理者ブリーフ。案件概要・4機能・制約         …所与
│  ├─ 13_meeting-flow.md         会議の4つの型と「次へ進む条件」               …所与
│  ├─ 20_requirements-draft.md   要件定義書のドラフト＝案件の最終成果物        …手書き
│  ├─ 21_screen-design.md        画面設計と承認フローの現在地                  …自動生成
│  ├─ 22_detail-spec.md          詳細仕様。承認済みの画面についてのみ書く      …手書き
│  ├─ 画面一覧・機能一覧.xlsx    納品物のExcel。4シート・承認状態は色分け      …自動生成
│  ├─ 90_ground-truth.md         ⚠️ 業務側の実態＝答え。client-boss と client-staff だけ
│  └─ 99_supervisor-checklist.md ⚠️ 監督専用。進行の質を採点する材料
│
├─ output/                       配布用の備忘。閉会のたびに1ファイル増える（**git 管理外**）
│  └─ 備忘_01.md                 第1回の1枚（目的・ゴール・決定・宿題・確定事実）      …自動生成
│
├─ scripts/                      DBを読み書きする。コマンドが裏で叩いている
│  ├─ db_init.py                 スキーマ作成と共通ヘルパ。他のスクリプトの土台
│  ├─ log.py                     発言を記録する。PostToolUse フックの実体でもある
│  ├─ record.py                  会議・決定・宿題・画面・機能・事実・状態を書き込む
│  ├─ views.py                   docs/01 02 03 04 21 をDBから再生成する
│  ├─ minutes.py                 output/備忘_NN.md を書き出す
│  ├─ query.py                   発言・決定・宿題・事実を横断検索する（/recall の実体）
│  ├─ export_excel.py            画面一覧・機能一覧のExcelを生成する（/excel の実体）
│  └─ clock.py                   会議の持ち時間と残りを計算する（/clock の実体）
│
└─ .claude/                      Claude Code の設定一式
   ├─ settings.json              下のフック2本と log.py の登録
   ├─ agents/                    5体のエージェント定義。性格と、読み書きできる範囲もここ
   │  ├─ client-boss.md          業務担当者（部長）
   │  ├─ client-staff.md         部長の部下
   │  ├─ sys-manager.md          システム管理者
   │  ├─ sys-staff.md            システム担当者
   │  └─ sys-junior.md           新人
   ├─ commands/                  スラッシュコマンドの手順書。15本（中身は「コマンド」の表）
   ├─ skills/                    作法。エージェントが必要になったとき自分で読む
   │  ├─ hearing/SKILL.md        要件を聞き出す作法。質問の型、仮決めの基準
   │  └─ screen-design/SKILL.md  画面設計の作法。ワイヤーフレーム記法、業務系UIの慣行
   └─ hooks/
      ├─ audit.py                90番台へのアクセスを記録する（ブロックはしない）
      └─ guard.py                自動生成ファイルへの直接書き込みを止める（ブロックする）
```

**自動生成** はDBから毎回まるごと書き直されるので、直接編集しても次の生成で消えます。
**手書き** は `sys-staff` が書く読み物で、`/reset` しても残ります。**所与** は会議前から置いてある固定の資料です。

**git に入るのは雛形だけです。** `docs/` の自動生成物は**空の状態**（「まだ会議は開かれていません」）でコミットしてあり、
会議で書き換わった分はコミットしません。**git管理外**の2つ（`docs/00_question-list.md` と `output/`）は
会議が始まってから生まれるので、雛形も置いていません。記録の正は `db/meeting.db` で、そこから何度でも再生成できます。

### docs/ の中身

**番号の頭が用途を表します。**

| 番号 | 用途 | 中身 | 性質 |
|---|---|---|---|
| **`00`番台** | **会議** | 進行と記録 | 会議のたびに変わる |
| **`10`番台** | **入力** | 会議前から置いてある所与の資料 | 固定。変わらない |
| **`20`番台** | **成果物** | プロジェクト中に育つもの | 積み上がる |
| **`90`番台** | **非公開** | 業務側の実態と監督用チェックリスト | **読んでよい人が限られる** |

#### 00番台 — 会議（進行と記録）

#### 自動生成と手書きの違い

**自動生成**（`01` `02` `03` `04` `21` と `.xlsx`）── `db/meeting.db` が正で、`scripts/views.py` と `scripts/export_excel.py` が**毎回まるごと書き直します。**

```bash
python scripts/views.py                    # 全部作り直す
python scripts/views.py --only decisions   # 決定ログだけ
python scripts/export_excel.py             # Excelを作り直す
```

**直接編集しても次の生成で消えます。** 中身を変えたいときはDBに書きます（`scripts/record.py`）。ファイル冒頭にも同じ警告のコメントが入っています。

**手書き**（`00` `20` `22`）── `sys-staff` が執筆する読み物です。DBからは再生成されないので `/reset` しても残ります（残すか消すかはリセット時に聞かれます）。決定の**一次情報は `02_decision-log.md`**（DB由来）です。`20` や `22` の記述と食い違ったら `02` が正です。

### output/ の中身 — 備忘

**会議1回につき1ファイル**、`備忘_01.md` `備忘_02.md` … と増えていきます。`/meeting-close` が最後に生成します。

`docs/` のビューは**種類ごとの縦串**（決定は決定、宿題は宿題で全会議分）です。それに対して備忘は**1回の会議の横串**で、
その日のことだけが1枚に載ります。あとから「あの回は何を決めたんだったか」を読み返すとき、会議に出ていない人に渡すときはこちらです。

| 載っているもの | なぜ載せるか |
|---|---|
| 目的・**本日のゴール**・総括 | ゴールは「誰が次に着手できるか」で書かれている。達成できたかが総括に出る |
| 参加者（**参加形態と発言数**） | 誰にもう聞けないか（opening は退席済み）。**full なのに発言0なら★が付く** |
| 決まったこと（**本決め／仮決めを分けて**） | 仮決めは「この前提で進めるが確定ではない」もの。混ぜると事故る |
| 持ち帰り（宿題）＝担当・期限つき | 担当と期限のない宿題は誰も抱えない |
| その回で確定した事実 | 次回以降の議論の前提になる具体値 |
| 次に開くべき会議 | `/meeting-open` にそのまま渡せる文面 |

**発言の原文は載せません。** 決定と事実には根拠発言のID（`u#NN`）が付いているので、必要なときだけ
`python scripts/query.py --utterance NN`（決定から辿るなら `--decision NN`）や `/recall` で引きます。

```bash
python scripts/minutes.py              # 全回を作り直す
python scripts/minutes.py --latest     # 直近の1回だけ
python scripts/minutes.py --meeting 2  # 第2回だけ
```

**これもDBが正の自動生成物です。**直接編集しても次の生成で消えます。

### scripts/ の中身

コマンドが裏で叩いているものです。直接使うこともできます。

| スクリプト | 役割 |
|---|---|
| `db_init.py` | DBとテーブルを作る（初回セットアップ） |
| `log.py` | 発言を記録する。`PostToolUse` フックとしても動く |
| `record.py` | 会議・決定・宿題・画面・機能・確定事実・状態を書き込む |
| `views.py` | DBから Markdown ビューを再生成する（`--only decisions` で一部だけ） |

## 規律と監査

`docs/90_ground-truth.md`（業務側の実態）を読んでよいのは `client-boss` と `client-staff` だけ、`docs/99_supervisor-checklist.md` は監督専用です。

- `90_ground-truth.md` をシステム側が読むと、**答えを知っている者が質問する**ことになります。聞き出す技術が要らなくなってシミュレーションとして無意味になり、業務側が「言っていないこと」をシステム側が知っている状態になって会話も破綻します
- `99_supervisor-checklist.md` は、シミュレーションが正しく機能しているかを監督が採点するためのものです。演者が読めば、そこに書かれた挙動をなぞるだけになります

技術的には読めてしまうので、これは規律です。ただし**破られたら分かるようにはしてあります。**

- `PreToolUse` フック（`.claude/hooks/audit.py`）が Read / Grep / Glob / Bash 経由のアクセスを全部記録し、`/status` が件数を報告します
- 会議中に業務側ペルソナを呼んだ回数と食い違っていれば、覗かれた疑いがあります
- ブロックはしません（業務側ペルソナは正当に読む必要があり、フックからは呼び出し元を判別できないため）

**逆に、ブロックするものもあります。** `docs/01` `02` `03` `04` `21` への直接の書き込みは `PreToolUse` フック（`.claude/hooks/guard.py`）が止めます。こちらは判断の余地がありません ── 自動生成物なので誰がいつ書いても次の `views.py` で消え、しかも消えるのは後になってからです。**記録では間に合わないものだけをブロックする**、というのがこの2本の使い分けです。

発言の記録も同じ思想です。`PostToolUse` フックが Agent / SendMessage の出力を `utterance` テーブルに自動で入れ、決定は根拠発言のIDに紐づきます。業務担当者が「そんなことは言っていない」と蒸し返したとき、**原文を引けるのがこの仕組みの要**です。
